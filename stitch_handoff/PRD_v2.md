# 투자사업 공사비 적정성 검토 AI 웹 서비스 PRD v2

문서 상태: 개발 기준안
작성일: 2026-09-09
대상: 광양5 사무동 1차 운영, 다중 프로젝트 확장
기술: Next.js, FastAPI, PostgreSQL, 파일 저장소, 비동기 작업 큐, Windows CAD 분석 워커

이 문서는 구현·테스트·운영 담당자가 같은 결과를 기대하도록 입력, 처리, 출력, 예외, 권한, 완료 조건을 고정한다. `PRD.md`의 방향을 유지하되 모호한 표현과 충돌을 제거했다.

## 1. 문제와 성공 결과

### 1.1 해결할 사용자 문제

| 사용자 | 현재 문제 | 서비스가 제공할 결과 |
|---|---|---|
| 공사부서 | 산식·수량·금액을 여러 엑셀과 도면에서 수작업 대조한다. | 재계산값, 차이, 경고, 원본 행/셀을 한 화면에서 확인하고 검토 의견을 남긴다. |
| 설계부서 | 기준/변경 도면의 Rev.와 변경 위치를 찾기 어렵다. | 전후 도면·시트·위치·좌표·변경 후보와 수량/내역 연결 후보를 확인한다. |
| 구매부서 | 신규내역의 비교 단가와 적용 조건을 찾기 어렵다. | 승인된 동일 프로젝트 참고단가, 공식 자료, 조달청 조회 결과를 출처·기준일과 비교한다. |
| 마스터(`pfm391`) | 승인 순서·자료 버전·감사 이력을 수작업 관리한다. | 전체 대기열, 예외 승인, 버전별 결과, 이력과 보고서 패키지를 관리한다. |

### 1.2 측정 가능한 MVP 목표

- 동일 프로젝트 내 원본 자료의 100%가 파일 해시와 추적 위치를 가진다.
- 승인 전 수량·금액·단가의 `confirmed` 값이 API/DB/UI/보고서에 생성되지 않는다.
- 공사→설계→구매 순서를 우회한 일반 사용자 요청은 100% 403 또는 409로 거절된다.
- 핵심 3개 파일(도면 1개, 내역서 1개, 수량산출서 1개) 업로드부터 규칙 결과 생성까지 1개 작업 ID로 추적된다.
- 모든 경고의 100%가 원본 위치 또는 “원본 위치 확인 불가”라는 명시적 상태를 가진다.
- 동일 입력 해시·동일 규칙 버전·동일 표준사전 버전 재처리 시 결정적 규칙 결과가 동일하다.

### 1.3 MVP에서 하지 않는 것

설비 이상탐지, 승인 전 자동 확정, 승인 전 학습 데이터화, 모든 DWG의 의미·좌표 자동 확정, 타 프로젝트 단가 자동 적용, ERP/전자결재 실행, 자율 승인 에이전트는 제외한다.

## 2. 범위와 데이터 격리

- 기본 프로젝트는 `광양5 사무동`이다. 프로젝트→건물→공사/공종→내역 항목 계층을 사용한다.
- 다른 프로젝트·다른 건물은 등록할 수 있다. 단, 모든 API와 DB 조회는 `project_id`를 필수 조건으로 하며 자동 혼합하지 않는다.
- 다른 프로젝트 자료는 사용자가 현재 검토 화면에서 `참고자료로 사용`을 명시한 경우에만 읽기 전용 후보로 표시한다. 자동 적용하지 않는다.
- 한 검토 세션의 범위는 프로젝트·건물(선택/전체)·공사/공종·자료 회차로 고정하고, 화면 상단에 항상 표시한다.

## 3. 사용자와 권한

MVP 운영 계정은 네 개만 사용한다. SSO/MFA와 추가 사용자 관리는 후속 범위다.

| 계정 | 부서/역할 | 조회 | 검토/쓰기 | 승인 |
|---|---|---|---|---|
| `pfc391` | 공사부서 | 전체 프로젝트 협업 범위 | 수량·산식·금액 경고, 의견, 근거 요청 | 공사 단계 |
| `pfe391` | 설계부서 | 전체 프로젝트 협업 범위 | 도면 변경 후보, Rev., 위치·적용범위 검토 | 설계 단계 |
| `pfp391` | 구매부서 | 전체 프로젝트 협업 범위 | 단가 조회·후보·적용 판단 | 구매 단계 |
| `pfm391` | 마스터 | 전체 | 사용자·규칙·사전·프로젝트·삭제·보고서 관리 | 모든 단계, 명시적 예외 승인 |

- 비밀번호는 Argon2 또는 bcrypt 해시만 저장한다. 초기 비밀번호는 시드 입력으로만 사용하고 첫 로그인 변경을 요구한다.
- 권한 확인은 `user`, `department`, `project_id`, 대상 상태를 모두 검사한다.
- 마스터의 단계 우회·삭제는 사유·대상·행위자·시각을 필수 입력으로 하고 append-only 감사 로그에 남긴다.

## 4. 핵심 업무 흐름

### 4.1 정상 흐름

```text
원본 업로드
 → 파일 검증·해시 저장
 → 비동기 전처리/표준화
 → 규칙 실행
 → 도면 변경·수량·금액·단가 후보/경고
 → 공사부서 검토·승인
 → 설계부서 근거 확인·승인
 → 구매부서 단가 검토·승인
 → 마스터가 확정 조건 확인 후 별도 확정 실행(선택)
 → PostgreSQL 이력·보고서 저장
 → 화면/과거 회차 재조회
```

### 4.2 자료 상태

`UPLOADED → VALIDATING → ACCEPTED → PREPROCESSING → LINKED → RULE_CHECKED`

`VALIDATING → REJECTED`, `PREPROCESSING/RULE_CHECKED → FAILED`도 허용한다. 실패는 재시도 가능 여부와 마지막 오류를 저장한다. 원본과 과거 결과는 삭제하지 않고 격리 또는 논리 삭제한다.

### 4.3 검토·승인 상태

검토 대상별 상태: `검토 대기 → 검토 중 → 승인/수정 요청/반려/추가자료 요청`.

승인 단계는 별도로 `CONSTRUCTION → DESIGN → PROCUREMENT → READY_FOR_FINAL`로 둔다. 한 대상의 부서 승인이 완료되어도 값의 `confirmation_state`는 `CANDIDATE` 또는 `PENDING`이다. `CONFIRMED`는 다음 조건을 모두 충족하고 마스터가 별도 확정 API를 실행한 경우에만 만든다.

1. 기준/변경 도면번호와 Rev. 확인
2. 위치·적용범위 확인
3. 수량산출서 산식 또는 행 확인
4. 내역서 항목 확인
5. 필요한 단가 근거 확인
6. 공사·설계·구매 단계 승인 완료

공사 승인 전 설계/구매 승인 요청은 409, 일반 사용자의 단계 우회는 403이다. 반려는 영향을 받는 가장 앞 단계로 되돌리고 이후 단계는 잠근다. 일괄 승인은 같은 프로젝트·같은 단계·같은 부서만 가능하며 항목별 성공/실패를 반환한다.

## 5. 자료 업로드·전처리·CAD

### 5.1 입력 계약

지원 형식은 PDF, DWG, XLSX, XLSM, CSV다. 업로드 시 다음을 필수로 받는다.

- 프로젝트·건물·공사/공종
- 자료 유형(기준 도면/변경 도면/내역서/수량산출서/단가 참고자료)
- 기준일, 도면번호·시트·Rev.(알 수 없으면 `UNKNOWN`), 기준/변경 구분
- 파일 원본명, 크기, MIME, SHA-256, 업로드자, 업로드 시각

초기 크기 한도는 PDF 1GB, DWG 500MB, XLSX/XLSM 200MB, CSV 500MB다. 시그니처·MIME·바이러스 검사·파일명 안전화에 실패하면 `REJECTED`로 격리한다. 암호화 PDF, 손상 파일, 매크로 실행, 외부 링크 자동 갱신은 실행하지 않고 제한 사유를 표시한다.

### 5.2 원본과 회차

- 원본 본문은 파일/오브젝트 저장소에 불변 경로로 보관하며 DB에는 경로/자산 ID와 추적정보만 저장한다.
- 동일 SHA-256 재업로드는 기존 파일·전처리 회차를 재사용하고 중복 감사 로그만 기록한다.
- 새 SHA-256 또는 새 Rev.는 새 `source_version`과 새 `preprocessing_run`, 새 `review_run`을 만든다. 과거 회차는 읽기 전용이다.
- 관리자는 기존 119/118/107 결과를 `legacy_import`로 가져올 수 있지만 일반 업로드를 대체하지 않는다. 가져온 자료는 승인 대기로 시작한다.

### 5.3 전처리 작업

원본 업로드 API는 짧은 검증만 수행하고 202와 `job_id`를 반환한다. PDF/OCR, XLSX 파싱, DWG 비교, 규칙 전체 실행은 작업 큐에서 처리한다. 기본 작업 제한시간은 30분, 자동 재시도는 일시 오류에 한해 최대 5회다. 작업에는 `attempt`, `progress`, `stage`, `retryable`, `error_code`, `input_hash`를 저장한다.

### 5.4 Windows CAD 분석 워커

ZWCAD·CAD 뷰어·기존 추출도구는 FastAPI/PostgreSQL과 분리된 Windows 워커에서 재사용한다. 워커 계약은 다음과 같다.

- 입력: 원본 자산 ID, SHA-256, 기준/변경 버전, 도구 실행 옵션
- 출력: 공통 `drawing_objects`, 변경 후보, 추출 결과 파일 Manifest, 결과 SHA-256
- 기록: 도구명·버전·라이선스/세션 ID·옵션·시작/종료·stdout/stderr 요약
- 오류: 도구 미설치, 라이선스 부족, 프로세스 고착, 변환 실패, 제한시간 초과를 각각 분류
- fallback: 워커가 없으면 파일 메타데이터·경로·Rev.만 저장하고 자동 변경 판정은 만들지 않는다.

## 6. 규칙 기반 검토

### 6.1 검토 항목

1. 산식 재계산: 산식 파싱값과 보고 수량 비교
2. 수량·금액: `금액 = 수량 × 단가` 재계산, 동/층/공간 집계 비교
3. 품명·공종·규격·단위·재질·강도 불일치
4. 기준/변경 도면번호·시트·Rev. 비교
5. 도면 변경 후보→수량산출서 행→내역서 항목 연결 후보
6. 신규내역 단가 후보와 출처 비교
7. 중복·누락·음수·0 단가·비정상 단위 경고

### 6.2 금액별 경고 기준

내역 금액은 부가세 제외 원화 기준이며 수량은 표준 단위 변환 후 비교한다. `차이율 = abs(검산값-원본값) / max(abs(원본값), 1)`로 계산하고 금액 차이는 원화 절대값으로 계산한다. 일반 경고는 두 조건 중 하나라도 만족하면 생성하고, 높음은 높음 조건을 만족하면 생성한다.

| 내역 금액 | 수량 일반/높음 | 금액 일반/높음 |
|---|---|---|
| 1천만원 미만 | 3% / 7% | 5% 또는 30만원 / 10% 또는 100만원 |
| 1천만원 이상~1억원 미만 | 2% / 5% | 3% 또는 100만원 / 7% 또는 300만원 |
| 1억원 이상 | 1% / 3% | 2% 또는 300만원 / 5% 또는 1,000만원 |

여기서 “또는”은 비율 조건 또는 절대금액 조건 중 하나만 충족해도 해당 등급으로 판정한다. 반올림은 계산 후 원 단위에서 한다. 도면 연결 미확인은 불가가 아니라 `연결 후보/추가 확인 필요`이며, 수량산출서·내역서 연결 미확인만 일반 경고로 표시한다. 임계값은 `rule_version`으로 고정한다.

### 6.3 경고 출력 계약

모든 `finding`은 category, severity, judgement, reason, confidence, rule_id/version, input_hash, original_value, normalized_value, project/building/work scope, status를 가진다. 근거가 있으면 파일 해시·파일명·시트·행·셀 또는 도면번호·시트·Rev.·페이지·좌표·객체 ID를 하나 이상 저장한다. 위치를 찾지 못하면 `locator_status=UNRESOLVED`와 확인 방법을 저장한다.

`confidence`는 0.00~1.00 후보 근거 강도이며 문자·규격·단위·위치·버전 일치 요소를 분해 저장한다. 확정 여부를 나타내지 않는다.

## 7. 단가 검토

적용 후보 순서는 다음과 같다.

1. 동일 프로젝트 다른 건물의 **승인 완료 참고단가**
2. 공식 조달청 CSV·표준시장단가
3. 위 자료가 없을 때 조달청 PriceInfoService API

타 프로젝트 단가는 `외부 프로젝트 참고`로만 표시하며 자동 후보로 만들지 않는다. 동일 프로젝트 참고단가는 품명·규격·단위·공종·적용조건이 일치해야 하고, 기준일 차이가 설정값을 넘으면 `시기 차이` 경고를 생성한다. 모든 자료는 발행기관, 기준일, 파일/응답 해시, 원본 행, 조회 파라미터를 기록한다.

API 결과 상태는 `NOT_REQUESTED`, `RUNNING`, `SUCCEEDED`, `NO_RESULT`, `CONFIG_ERROR`, `AUTH_ERROR`, `FORBIDDEN`, `SCHEMA_ERROR`, `TIMEOUT`, `RATE_LIMITED`, `UPSTREAM_ERROR`, `RETRY_PENDING`으로 구분한다. 어떤 출처도 승인 전 내역 단가를 덮어쓰지 않으며, 구매 검토 결과는 `적용 후보` 또는 `적용 보류`로 저장한다. 비고에는 `대체자료 적용`, 출처, 기준일, 적용 사유를 기록한다.

## 8. 챗봇 범위

챗봇은 읽기 전용 근거 검색 도우미다. 세션 생성 시 프로젝트·건물·공사 범위를 고정하며, 매 메시지마다 권한을 다시 검사한다.

- 지원 질문: 현황, 경고 설명, 도면 변경 후보, 수량 재검산, 단가 후보 비교, 승인 이력, 근거 찾기
- 처리: PostgreSQL 검색 → 필요한 페이지/시트/행/객체 추출 → 규칙 엔진 읽기 전용 도구 호출 → 답변 생성
- 답변 필드: `answer`, `answer_state`, `confidence`, `citations`, `next_actions`, `request_id`
- 답변 상태: `근거 확인`, `검토 후보`, `추가 확인 필요`, `권한 부족`, `처리 실패`
- 반드시 원본 파일·해시·위치·Rev.·신뢰도 링크를 인용한다. 근거가 없으면 추정하지 않는다.
- 승인·반려·단가 확정·원본 수정 요청은 실행하지 않고 검토 화면으로 안내한다.
- 외부 모델 사용은 기본 OFF다. 허용 시 원본 전체가 아닌 allowlist 추출 조각만 전송하고 모델명·프롬프트 버전·전송 필드·보존기간을 감사한다.

챗봇은 규칙 엔진과 파일 추적성이 먼저 합격한 뒤 활성화한다. 모델 장애 시 근거 목록과 규칙 결과를 보여주는 대체 응답을 사용한다.

## 9. 논리 데이터 모델

핵심 테이블은 `users`, `departments`, `projects`, `buildings`, `work_packages`, `source_files`, `document_versions`, `processing_jobs`, `preprocessing_runs`, `preprocessing_records`, `preprocessing_artifacts`, `estimate_items`, `quantity_items`, `quantity_aggregates`, `drawing_objects`, `drawing_change_candidates`, `mapping_candidates`, `review_runs`, `findings`, `evidence_links`, `price_sources`, `price_candidates`, `price_reviews`, `approvals`, `audit_logs`, `reference_dictionaries`, `review_exports`, `chat_sessions`, `chat_messages`, `chat_citations`, `chat_tool_runs`다.

- 운영 데이터와 원본 메타데이터는 PostgreSQL에 저장한다. 원본 본문은 저장하지 않는다.
- `review_runs`, `preprocessing_runs`, `approval_events`, `audit_logs`는 append-only다.
- 수량·단가·금액은 `original`, `normalized`, `candidate`, `confirmation_state`를 분리한다.
- 모든 결과는 source file hash, parser/rule/dictionary version, input hash, created_at을 참조한다.

## 10. API 계약

모든 API는 인증, 프로젝트 권한, Pydantic 입력 검증, `request_id`, 페이지네이션, 표준 오류(`code`, `message`, `details`, `retryable`)를 사용한다.

| 영역 | 메서드/경로 | 입력·출력 핵심 |
|---|---|---|
| 상태 | `GET /health`, `GET /api/v1/projects`, `GET /api/v1/projects/{id}` | 서비스/DB 상태, 프로젝트 현황 |
| 자료 | `POST/GET /api/v1/projects/{id}/files` | 메타데이터·검증 상태, 업로드는 202 가능 |
| 전처리 | `POST /api/v1/projects/{id}/preprocessing/run`, `GET /api/v1/jobs/{job_id}` | 원본 선택, 작업 상태·진행률·재시도 |
| 결과 | `GET /api/v1/projects/{id}/preprocessing`, `/findings`, `/drawings/changes`, `/quantities`, `/mappings` | 필터·페이지네이션·회차 |
| 근거 | `GET /api/v1/findings/{finding_id}/evidence` | 파일 자산 ID와 보안 다운로드 링크 |
| 승인 | `POST /api/v1/reviews/{review_id}/approvals`, `POST /api/v1/projects/{id}/reviews/approvals/batch`, `GET /api/v1/projects/{id}/approval-queue` | 단계·권한·필수 의견·멱등키, 항목별 결과 |
| 단가 | `POST /api/v1/projects/{id}/prices/lookup`, `GET /api/v1/projects/{id}/prices/results`, `POST /api/v1/price-candidates/{id}/review` | 출처·오류·후보, 자동 적용 금지 |
| 이력 | `GET /api/v1/projects/{id}/review-history`, `GET /api/v1/projects/{id}/audit-logs` | 회차·상태·행위자·기간 |
| 챗봇 | `POST/GET /api/v1/projects/{id}/chat/sessions`, `POST/GET .../messages`, `GET .../citations` | 근거 인용 답변, 장기 작업 202 |
| 보고서 | `POST/GET /api/v1/projects/{id}/reports`, `GET .../{export_id}/download` | 한 스냅샷의 PDF·Excel·Manifest |

파일 다운로드는 실제 경로를 노출하지 않고 권한 검증 후 단기 서명 URL 또는 스트리밍으로 제공한다. 승인·삭제·단가 확정 API는 관리자 또는 해당 부서만 호출할 수 있다.

## 11. 화면 요구사항

1. 프로젝트 현황 대시보드: 범위 필터, 작업/경고/승인 상태, 최신 회차
2. 자료 업로드·버전: 파일 검증, 해시, 기준/변경, Rev., 작업 상태
3. 도면 변경 검토: 전후 비교, 후보, 위치, 원본 열기, 연결 후보
4. 수량·산식·금액 검토: 산식, 재계산, 차이율/차이금액, 원본 행/셀
5. 신규내역 단가: 세 출처 후보, 기준일, 오류, 적용 후보/보류
6. 승인 대기열: 단계별 개별/선택 일괄 처리, 항목별 성공/실패
7. 경고·근거 패널: 사유, 규칙 버전, 원본 위치, 신뢰도, 이력
8. 검토 이력·감사 로그: 회차, 상태 전이, 의견, 사용자, 시각
9. 챗봇: 고정 범위, 인용 링크, 근거 없음 상태, 검토 화면 이동

승인 전 수량·금액·단가는 모든 화면·API·Excel·PDF에서 `후보값/승인 대기/확정 전`으로 표시한다. 확정 스타일은 명시적 최종 확정 이후에만 사용한다.

## 12. 오류와 예외 처리

| 오류 | 코드/HTTP | 시스템 동작 | 사용자 조치 |
|---|---|---|---|
| 확장자·시그니처·크기 불일치 | `FILE_INVALID` 422/413 | 격리, 원본 해시 보존 | 형식/크기 수정 후 재업로드 |
| 바이러스 검사 불가/감염 | `MALWARE_SCAN_FAILED` 422 | 접근 차단 | 관리자 확인 |

| 스키마·OCR·DWG 파싱 실패 | 작업 `FAILED` | 단계/파일/페이지 기록 | 재시도 또는 수동 입력 |

## 13. 보안·보존·운영

- TLS, 저장 암호화, 조달청 키/DB 비밀번호 비밀 저장소, 업로드 악성코드 검사를 사용한다.
- 프로젝트·건물·공사 조건을 모든 쿼리에 포함한다. 감사 로그는 애플리케이션 사용자가 수정할 수 없다.
- 원본·전처리·검토·승인·감사 데이터는 기본 7년 보존한다. 보존기간 중 법적 보류 플래그가 있으면 물리 삭제하지 않는다.
- 논리 삭제는 마스터만 가능하며, 물리 삭제는 보존정책·법적 보류·백업 상태 확인과 2단계 확인 후에만 한다.
- 백업은 일 1회 증분·주 1회 전체로 하고, RPO 24시간·RTO 8시간을 목표로 월 1회 복구 테스트한다.
- 보고서 Manifest에는 원본 파일명·해시·자산 ID·위치·규칙 버전·승인 상태를 넣되 원본 본문은 복사하지 않는다.

## 14. 비기능 요구사항

- 목록/조회 API: 시험 데이터 10만 경고, 동시 20명, p95 2초 이하(외부 연계 제외)
- 업로드 접수: 파일 검증 후 5초 이내 202 반환(실제 분석 시간 제외)
- 작업: 30분 제한, 일시 오류 최대 5회 재시도, 진행률과 마지막 오류 제공
- UI: 서버 페이지네이션/가상 스크롤, 한국어, 키보드 접근성, 색상 외 텍스트 심각도 표시
- 챗봇: 근거 검색 질문 p95 10초 이내, 초과 시 202 작업 또는 규칙 결과 fallback
- 재현성: 동일 입력/버전 fixture 3회 실행 결과의 경고 유형·판정·근거 ID가 동일

## 15. 완료 조건과 테스트

### 15.1 Given/When/Then 인수 기준

- Given 정상 도면·내역서·수량산출서, When 업로드하면, Then 각각의 해시·버전·작업 ID가 저장되고 규칙 결과가 생성된다.
- Given 공사 승인 전, When 설계/구매 승인 API를 호출하면, Then 409/403이며 상태가 변하지 않는다.
- Given 승인 전 단가 후보, When 화면/API/보고서를 조회하면, Then `candidate` 또는 `pending`이고 확정 단가 필드가 없다.
- Given 동일 SHA-256 재업로드, When 전처리를 요청하면, Then 기존 회차를 반환하고 중복 감사만 추가한다.
- Given 다른 Rev. 파일, When 재처리하면, Then 새 회차가 생성되고 과거 승인 이력은 변하지 않는다.
- Given 조달청 401/403/빈 결과/429/타임아웃, When 조회하면, Then 각 상태 코드와 재시도 가능 여부가 구분된다.
- Given 경고 한 건, When 근거를 조회하면, Then 파일 해시와 시트/행/셀 또는 도면 위치가 반환되거나 `UNRESOLVED`가 명시된다.
- Given 일괄 승인 3건 중 1건이 최신 상태와 충돌, When 처리하면, Then 2건만 성공하고 1건의 실패 사유를 반환한다.
- Given 챗봇이 근거 없는 질문을 받으면, When 답변하면, Then `추가 확인 필요`이고 가상 수치·파일 위치를 만들지 않는다.
- Given 과거 회차, When 재조회하면, Then 새 규칙 실행으로 값이 변경되지 않는다.

### 15.2 테스트 묶음

단위(산식·단위·임계값·상태 전이), API(2xx/4xx/409/5xx·권한·멱등성), 파일(위조 확장자·대용량·중복·손상), 워커(CAD 성공/라이선스/timeout/fallback), 외부 단가(성공·각 오류), 승인(순서·반려·추가자료·일괄 부분 성공), DB(트랜잭션·재조회·백업 복구), UI(경고/근거/오류/접근성), 챗봇(권한 격리·인용·근거 없음·쓰기 요청 거부)을 자동화한다.

## 16. MVP 출시 범위와 후속

### MVP 포함

원본 업로드·검증·보존, 비동기 전처리 연결, 규칙 기반 검산/경고/도면 후보/단가 후보, 원본 추적, 공사→설계→구매 승인, 선택 일괄 승인, PostgreSQL 이력, Next.js 화면, 보고서 패키지, 제한형 읽기 전용 챗봇, 통합 테스트.

### 후속

정확도 라벨셋 기반 DWG 의미 해석, 승인 완료 데이터 기반 연결/경고 우선순위 모델, SSO/MFA, 회사 전자결재·전자서명, ERP/발주 연계, 자율 실행형 에이전트.

## 17. 확정이 필요한 운영값

다음 값은 기본값으로 시작하되 배포 전에 마스터가 확인한다: 실제 파일 저장소/백업 위치, 공식 CSV 갱신 주기·스키마, 조달청 운영 키·호출 한도, 사업장 보존정책, 3영업일 SLA의 공휴일 캘린더, CAD 워커 설치 PC와 라이선스 동시 수, 외부 챗봇 모델 사용 허용 여부.

이 문서의 “후보”, “검토 대기”, “추가 확인 필요”는 판단을 돕는 상태이며 공사비의 공식 확정값이 아니다.
